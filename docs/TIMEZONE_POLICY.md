# Политика дат и часовых поясов

## Три разных смысла даты

| Вид | Где используется | Правило |
| --- | --- | --- |
| Момент времени | `utc_now()`, `created_at`, `updated_at`, журнал, TTL, ревизии ежемесячных расходов | UTC; старые naive datetime читаются через `as_utc()` как UTC |
| Банковская календарная дата | `Payment.payment_date`, даты начислений, покупок Сплита и графика | DATE без часового пояса; введённая или импортированная дата сохраняется и выводится без сдвига |
| Дата календаря аккаунта | Начисления на сегодня, финансовая сводка и план, платежи по умолчанию, генерация расходов, цели, активный месяц истории, автомобили | `financial_today(owner)` |

Доходы (`Income.income_date`), расходы (`Expense.expense_date`), переводы
в цели (`transaction_date`), замеры пробега и даты документов автомобилей
тоже хранятся как DATE. Часы используются только при выборе значения
«сегодня», а не при чтении сохранённой даты. Сервисы создания платежей
и переводов передают дату явно; резервные ORM-default `date.today` в
моделях не используются для определения даты финансового экрана и
в этой задаче не изменяются. Служебный updater имеет собственные UTC-часы
для статуса обновления; это не календарь финансовых операций.

`financial_today` выбирает валидный `User.timezone`, затем валидный
`APP_TIMEZONE`, затем UTC. Без контекста приложения резервный пояс — UTC.
В HTTP-запросе без явного владельца используется текущий пользователь;
обработка команд бота задаёт владельца через `account_calendar`.
Фоновые операции с данными аккаунта передают владельца явно. Генератор
ежемесячных расходов без заданного месяца определяет месяц отдельно для
каждого владельца. Поле `target_month` общего отчёта остаётся месяцем
приложения; это не ограничивает индивидуальные месяцы генерации.

Источник момента — `app.time_utils.utc_now()`. Для управляемого запуска
можно передать в конфигурации приложения `UTC_NOW_PROVIDER`: callable без
аргументов, возвращающий datetime (naive трактуется как UTC). Для отдельного
преобразования `financial_today(..., now=instant)` принимает явный момент.
`MONTHLY_EXPENSES_TODAY` сохранён как прежнее явное переопределение даты
генератора. При явных `today`, `as_of` или целевом месяце вычисления не
обращаются к часам для выбора календарной даты.

## Браузер, API и Telegram

Веб и Telegram Mini App используют один аккаунт и те же серверные расчёты.
Часовой пояс устройства не переопределяет пояс аккаунта. Сервер передаёт
`data-financial-date`; `/api/calendar-date` позволяет странице обновиться
после смены дня. API долга возвращает дату расчёта `today`. Строки DATE
форматируются как календарные даты, без преобразования в UTC.
Дневной лимит рассчитывается сервером на ту же дату, что и задолженность.

Ежемесячные напоминания используют `User.timezone` и `reminder_time`.
Автомобильные напоминания имеют отдельные настройки расписания
`notification_timezone` и `notification_delivery_time`. Пояс доставки
автомобильных напоминаний не переопределяет пояс финансового экрана.
Планировщики преобразуют реальный UTC-момент
в пояс доставки; это сохраняет существующую обработку DST и дедупликацию.

## Проверенные дефекты и границы изменения

Расходы ранее выбирали месяц и границу будущих записей по `APP_TIMEZONE`,
автомобили — дату приложения, а цели и активный месяц истории — дату ОС.
Например, в 22:30 UTC 31 декабря московский аккаунт уже находится в январе,
но фоновый генератор с `APP_TIMEZONE=UTC` ещё не создавал январские расходы.
Теперь выбор учитывает владельца. В расчёте Сплита без договорной даты
платежа запасной день брался из часов даже при явной контрольной дате;
теперь он берётся из переданного `today`.

Основные сервисы долга, платежей, сводки и плана уже использовали общий
календарь до этого изменения. Тест 04.11.2026 23:13 UTC подтверждает
05.11.2026 02:13 для Europe/Moscow. Добавлены проверки полуночи, нового
года, DST Europe/Tallinn, неизменности сохранённых DATE, индивидуальных
месяцев фоновой генерации и согласованности веб/API/Mini App.

Миграция и пересчёт исторических записей не требуются. Для развёртывания
достаточно обычного обновления приложения; база IANA поставляется через
существующую зависимость `tzdata`.
